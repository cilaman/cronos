# Delivery/v2 Pipeline — Goal↔Pipeline State Integration Assessment

## 1. Verdict

Your diagnosis is correct, and the mechanism is now precisely identified. The goal layer and the pipeline do not share a state contract — they share five untyped strings (`running/done/failed/blocked/escalated`) whose meanings are defined nowhere and interpreted differently by every consumer. Three specific consequences produce every symptom you reported:

1. **"The goal spawns wrong delivery pipeline nodes."** The runner's resume seeding (`runner/core.py:116-134`) treats every outgoing edge of every persisted-`done` node as fired, **without evaluating edge conditions**. Since every human sign-off forces a park→resume cycle, every conditional branch downstream of a sign-off fires unconditionally on resume. On the shipped spec, `frontend` runs after `signoff-scope` regardless of `has_ui`. Confirmed by repro D1. Two further defects guarantee the conditions could not have been evaluated correctly anyway: node `fields` are silently dropped by persistence (D2 — `lib/state/store.py:41-63` serializes `status/attempt/artifact_paths/gate/telemetry` but never `fields`; `CronosStateOps.write` at `adapters/cronos/adapter.py:99-135` likewise), and JSON booleans stringify to `"True"`, which matches neither `== true` nor `== false` (D3).

2. **"Falls to waiting because it thinks the delivery node failed despite the node delivering successfully."** The node's success/failure classification travels through a channel that discards it: the agent's `node_status` fence must survive inside `final_text_snippet`, which is a **head-truncation to 2,000 characters** of the agent's final message (`trace_parser.py:37-40, 376`). Agents write prose first and the fence last; any final message over ~2,000 chars loses the fence (D8). The adapter then falls back to an mtime-newest filesystem scan, and if that misses, returns `status="failed"` (`adapters/cronos/adapter.py:348-356`) → node failed → run failed → goal WAITING with "a node returned status=failed". The work was done; the classification channel dropped the receipt. Commit `28cbb26` raised the limit 500→2,000 — a symptom fix; the fence is still one long paragraph away from being lost.

3. **The inverse misclassification also exists.** The `node_status` vocabulary is explicitly open ("any non-empty string", `lib/node_status.py:77-81`), but `_dispatch_agent` maps only `blocked` and `failed` specially — **everything else, including `"wait"`, `"error"`, `"partial"`, becomes node `done`** (`runner/dispatch.py:143-154`, repro D4). A fail-open classifier on one side, a fail-closed one (missing fence → failed) on the other. Neither endpoint validates against a closed vocabulary.

The deeper architectural finding: because the package exports no semantics with its statuses, **the host must reverse-engineer what the runner meant** — which is exactly what `delivery_driver.py` has become. It did not exist at the delivery merge; it was created 2026-06-30 and grew to 624 lines in three days, 11 of the 40 post-merge commits touching it. It now contains three resume heuristics (`_resume_from_blocked`, `_resume_from_failed`, `_resume_from_stalled_gate`), two sidecar JSON counter files, and a post-hoc "was this `done` actually done?" gate inspection (`_stalled_gate_ids`). Every one of these is host-side compensation for missing package semantics — and none of it would exist for a standalone embedder, who would rediscover each failure mode from scratch. The proof that this is structural, not incidental: the repo already contains a **second** embedding (the harness path, `run_executor.py:568-728`), and it maps the same terminal statuses **differently** — `failed` and `escalated` harness runs finalize the task as **DONE** (`run_executor.py:715-727`), while the delivery driver maps them to WAITING. Same runner, same five strings, two hosts, two contradictory interpretations.

**Your fear about fix accretion is confirmed and quantified.** The fixes concentrated at the seam (driver 11 commits, adapter 11 commits, `run_executor` 10) while the runner whose semantics cause the failures received 3. Layer-by-layer: the completeness invariant is still absent from the runner (`runner/core.py:292-298` reports `done` unconditionally when the work-list drains, repro D5); the driver detects only the *gate* flavor of dead-ending, post-hoc. The gate node status is written twice with conflicting values — the adapter writes `needs_fix` (`adapter.py:425-445`), the runner immediately overwrites with `done` (`core.py:193-208`), and the event log records a phantom `needs_fix→done` transition. `reset_downstream_nodes` (`runner/loop.py:107-133`) — the documented stale-scope protection — has **zero callers**. The `"cancelled"` status checked by the runner's guard (`core.py:145`) is written by nothing and is not even a legal `WorkflowState.status` value. The CC-v1 `delivery` branch in `dispatchAgent` (`adapter.py:322-330`) is dead — `run_delivery_child` hardcodes `{"delivery": None}` (`run_executor.py:1549`). Meanwhile **548 package tests pass** at HEAD (up from 520 at your last review) alongside nine one-page repros.

## 3. Why 548 green tests coexist with this

Three structural reasons, all visible in `packages/delivery-workflow/tests/`:

**Synthetic executors bypass the seams.** Runner tests drive `run()` with in-memory executors and in-memory state that (unlike `CronosStateOps` + `StateStore`) round-trips `fields` — so D2 is invisible. No package test performs the park→driver-resume→re-run cycle, so D1 (a property of the *composition* of runner seeding with driver resume) has no test that could catch it.

**The tests assert the code, not the spec.** There is no executable statement anywhere of "when the work-list drains, every node is either executed or excluded by an evaluated-false condition," or "an agent status outside {done, blocked, needs_fix, failed} is a protocol error." Absent invariants can't fail.

**The lifecycle under test is single-process.** Everything that breaks here breaks *across* process boundaries (persistence, resume, re-entry) or *across* the app/package seam (fence transport, driver heuristics). The shipped spec's mandatory human nodes make multi-process the normal case in production and the untested case in CI.

The countermeasure remains what was recommended last cycle and is now the second item in the remediation plan: a **spec-conformance suite** that runs the shipped `delivery.workflow.yaml` through scripted park/resume cycles against real `StateStore` persistence, asserting the executed-node set and terminal outcome per scenario. Repros D1–D9 in the included script are the seed corpus for it.

## 4. Fix-accretion audit

Post-merge churn (commits touching file, `76fab0d3..HEAD`): `delivery_driver.py` 11 (created mid-window, now 624 lines), `adapters/cronos/adapter.py` 11, `run_executor.py` 10, `runner/core.py` 3, `runner/dispatch.py` 3. The pattern is consistent: when a runner semantic produced a bad goal state, the fix landed as a driver/adapter heuristic rather than a runner semantic change. Concrete instances of the pattern, each individually reasonable-looking, jointly a second implicit state machine living in the host:

- Runner has no completeness invariant → driver post-hoc `_stalled_gate_ids` (gates only) + WAITING reinterpretation of `done`.
- Runner can't resume past `blocked` → driver `_resume_from_blocked` with "any re-entry = approval".
- Persistence drops `attempt` semantics across resumes → sidecar `failed_resumes.json` counter.
- Gate always persists `done` → sidecar `stalled_gate_resumes.json` + reset-to-pending heuristic.
- Fence lost to truncation → raise limit 500→2,000 (`28cbb26`), widen fallback scan, add slug scoping, add class scoping (`f56cfad`) — four patches on an inference chain instead of removing the truncation from the classification path.
- lib.gate wrote statusless node entries → disabled by *not passing* `state_path` (`adapter.py:414-424`) + a defensive default in `_deserialize` (`store.py:20-26`) — the third writer was silenced, not removed.

None of these should survive remediation as-is; `03-remediation-plan.md` maps each to the package-level change that deletes it.
