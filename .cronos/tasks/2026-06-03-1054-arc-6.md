# Brief

# Arc 6 — Harnesses (Visual Agent Workflows): Execution Plan

## Context

Cronos-ready breakdown for **Arc 6** of the
[roadmap](let-s-discuss-key-features-async-hopcroft.md). A **Harness**
is a DAG executed by Cronos: authors compose nodes on a visual canvas,
Cronos runs the DAG, and a live overlay animates execution.

**Node types.** **Agent** — run a registered agent/skill with a prompt
template + variable bindings. **Trigger** — manual / cron / event
(task-state, webhook, file change, inter-node message). **Decision** —
branch on STATUS, output regex, or variable compare. **Wait** — human /
time / upstream signal. **Aggregator** — join N upstreams; emit on all
(or any).

**Persistence.** Each Harness is YAML at
`{space}/.cronos/harnesses/<name>.yml` (markdown-as-truth); editor +
runtime read it, editor writes it.

**Runtime.** A run is a first-class Task (`type=goal`) with one child
task **per Agent node** (reusing Arc 1 hierarchy + the worker model).
Each step's trace links to the run via a new `parent_run_id` field;
control-flow nodes are **not** tasks (see crux).

**Editor (UI).** React Flow, Cronos paper/ink palette matching current
Card styling. Differentiator = a **live-execution overlay**:
active node pulses, completed edges thicken, failed paths desaturate;
click a node → its agent's live log
([ConversationStream.tsx](frontend/src/components/ConversationStream.tsx)).

### Why this shape

Fed to Cronos as **one umbrella goal + eight subgoals**, each its own
CC-v1 pipeline (scout→analysis→design→impl→test→review→doc, via
[`/pipeline-scaffold`](.claude/skills/pipeline-scaffold/)). The
pipeline's analyst/architect phases produce the per-subgoal code design;
this doc decomposes Arc 6 into pipeline-sized, ordered requests and bakes
in the load-bearing decisions.

### Locked decisions

- **8 subgoals**, each a CC-v1 pipeline. Granularity keeps every
  architect within its 3–8 iteration budget (>12 ⇒ `status=partial`).
- **One shared branch** `feature/arc-6-harnesses`. No per-subgoal merge:
  each doc phase **commits-only** (swap scaffold's `/goal-finalize` for
  `/goal-task-commit`); a single **final task** runs the whole-arc suite
  then auto-merges to `main`.
- **Agent nodes bind to any registered agent/skill** (built-in or
  adopted) via the existing registry in
  [api/tools.py](backend/app/api/tools.py) (`_scan_category` /
  `_scan_skills`). **No Arc 5b dependency.**
- **Subgoals run sequentially** (6.1→…→6.8): each scout `depends_on` the
  prior subgoal's doc task, so only one pipeline edits the branch /
  `harnesses/` at a time.

### Load-bearing decisions (baked into the briefs)

1. **Only Agent nodes become child Tasks; control-flow nodes are
   evaluated in-process by a NEW interpreter — not `_run_goal`
   wholesale.** `_run_goal` ([worker.py:682](backend/app/worker.py#L682))
   has only recurse-goal / `run_agent`-task branches, and
   [agent.py](backend/app/agent.py) always spawns `claude -p`; a
   Decision/Wait/Aggregator node must not. The executor (6.2) is a new
   stateful interpreter reusing `run_agent` + `_finalize_child` +
   `_topo_children` for Agent nodes only, evaluating control-flow nodes
   itself between enqueues. **The crux of the arc.**
2. **`parent_run_id` is a `RunTrace` field, not a DB column.** Traces
   are JSON files
   ([trace_store.py](backend/app/trace_store.py) writes
   `.cronos/traces/{task_id}/{run_index}.json`). Add it to `RunTrace`
   ([trace_parser.py:110](backend/app/trace_parser.py#L110)), thread
   through `extract_run_trace`, expose in the traces API without
   breaking `TracePanel.tsx`.
3. **Overlay reuses existing SSE, not polling/websockets.** `worker.py`
   has `subscribe`/`sse_events`/`_run_buffer` replay;
   `ConversationStream.tsx` consumes `/api/tasks/{id}/stream`. The
   overlay subscribes to each Agent child's stream + a new run-level
   stream.
4. **6.1 ships a forward-compatible model**: per-node `position {x,y}`,
   `ports`/socket-ids, free-form `data` dict **now**, so 6.7/6.8 extend
   it *additively* — never revising an already-committed file (the only
   real failure mode of a shared-branch sequential build).

### Prerequisites

- **Arc 1** (hierarchy: `type`/`parent_id`/`depends_on`) — already in
  `main`. **NOT Arc 5b** — Agent binding uses the existing tool registry.

>   atomic write (tmpfile + `os.replace`) per
>   [space_storage.py](backend/app/space_storage.py). Path-safe
>   filename; name uniqueness.
> - Validator: graph is a DAG (no cycles), edges reference existing
>   nodes/ports, only allowed types. **Adapt** (do not reuse verbatim)
>   the cycle logic in [storage.py](backend/app/storage.py)

> - CRUD `backend/app/api/harnesses.py` wired into
>   [main.py](backend/app/main.py), following DI+auth in
>   [api/tasks.py](backend/app/api/tasks.py):
>   `GET/POST/PUT/DELETE /api/spaces/{id}/harnesses[/<name>]`. Invalid
>   graph ⇒ 422. Resolve YAML round-trip fidelity vs editor as
>   second writer (last-writer-wins) and concurrent CRUD vs a live run.
>
> Acceptance: POST a 3-node/2-edge harness → GET round-trips losslessly;
> a cycle or dangling edge → 422; on-disk YAML matches the API payload.

## 6.2 — Harness executor core (the interpreter)
**depends_on:** 6.1 · **has_ui:** false

**Request:**
> Build the runtime in `backend/app/harnesses/executor.py`. A run is a
> Task (`type=goal`); **only Agent nodes become child tasks.**
> - **Do NOT reuse `_run_goal` wholesale** (only recurse/`run_agent`
>   branches exist). Build a **new stateful DAG interpreter** walking the
>   graph: at an Agent node, materialise/enqueue a child Task and await
>   its terminal state (reuse `run_agent` + `_finalize_child` + the
>   topo-sort from `_topo_children`
>   [worker.py:51](backend/app/worker.py#L51)). Stub control-flow nodes
>   as pass-through here (6.3 implements them) so a linear all-Agent
>   harness runs end to end.
> - **Agent binding:** compose `agent_ref` + `prompt_template` +
>   resolved `variable_bindings` into the child Task `brief` (skills get
>   a `/<name>` prefix); resolve `agent_ref` against
>   [api/tools.py](backend/app/api/tools.py). No new `--agent` flag.
> - **Variable/data passing:** define how an upstream node's output
>   (child `RunTrace.final_text_snippet` / STATUS) flows into a
>   downstream node's `prompt_template` variables.
> - **`parent_run_id`:** optional field on `RunTrace`
>   ([trace_parser.py:110](backend/app/trace_parser.py#L110)); thread
>   through `extract_run_trace`, set on each Agent child, persist in the
>   trace JSON without breaking `TracePanel.tsx`.
> - Run state (per-node status, chosen edges, child ids) persists at
>   `{space}/.cronos/harness-runs/<run_id>.json` (restart-safe).
> - Address worker contention: a run holds the space's single serial
>   worker ([worker_pool.py](backend/app/worker_pool.py)) for its whole
>   duration — avoid starving normal tasks.
>
> Acceptance: a 3-node linear harness expands to a goal + 3 child tasks
> in topo order; each child's `parent_run_id` = run id; an upstream
> output is interpolated into the next prompt; run-state file reflects
> per-node status.

## 6.3 — Control-flow node semantics
**depends_on:** 6.2 · **has_ui:** false

**Request:**
> Implement the three control-flow evaluators in the interpreter. These
> run **in-process; never a subprocess, never a child task.**
> - **Decision:** branch on the upstream Agent signal — STATUS marker
>   (already in `AgentResult.status`), regex on `final_text_snippet`, or
>   harness-variable compare. Define precedence + missing-signal
>   behaviour; pick the outgoing edge by `condition` label.
> - **Wait:** human (map to `TaskState.WAITING` + resume via the
>   existing reply/`pending_messages` mechanism), time (resume after N),
>   or upstream signal.
> - **Aggregator:** join N upstreams; emit on **all** or **any**
>   (configurable). Define partial-failure semantics.
> - Reject/bound Decision-edge cycles in the 6.1 validator; add an
>   unbounded-wait guardrail.
>
> Acceptance: a Decision routes to edge A on `STATUS: DONE`, edge B on
> `STATUS: BLOCKED`; Aggregator `all` waits for both, `any` fires first;
> Wait(human) parks in WAITING and resumes on reply.
